# 一节课的数据生命周期

写给要改课堂页、结束课堂提交、补录或「编辑上课记录」的开发者：一节课的数据从开课到落库怎么流动，哪些约束不能破。

## 本地优先

整节课跑在老师浏览器本地，课中不与服务端通信。只有「结束课堂」时把整节课一次性提交，服务端在单个事务里落库。这样教室网络抖动不影响上课，代价是课中数据只存在于那台电脑的 localStorage 里。

本地课堂按班级占一个槽位（`nce.classroom.<classId>`），同一个班同一时间只能有一节进行中的课堂。

## 进入课堂页的判定顺序

打开 `/classes/:id/classroom` 时依次判断：

1. 本地已有该班进行中的课堂 → 恢复。若 URL 带 `?edit_id` 且与本地课堂不是同一节，显示冲突拦截页，不覆盖本地数据。
2. URL 带 `?edit_id=<sessionId>` → 拉取该节课的原始记录，还原成可编辑课堂（见「编辑上课记录」）。
3. URL 带 `?lesson=4&title=...&duration=120` → 直接开一节新课。
4. 以上都不是 → 跳课前配置页。

## 计分与奖章

个人分和组分都不落地存储，由 ±1 的计分事件流派生。组分 = 该组当前到堂组员的个人分之和 + 直接给小组的加减分，组员看的是当下（落库后是最终）分组，所以课中调组时学生已得的分会跟着他换组；计分事件上记的「加分时所在组」只作历史，不参与组分。未到堂、未分组的学生不计入任何组分。奖章同理：课中本地只存奖章名，结束课堂时随提交入库——机构奖章库按名字幂等 upsert，同时给这节课存一份快照。

## 结束课堂

- **幂等**：每节课带一个客户端生成的 `client_session_id`，重试时不变；重复提交返回已有的 session，不会建出两节课。
- **默认分组回写**：用下课时的分组覆盖班级默认分组，所以课中调组会延续到下节课。
- **提交前备份**：提交内容先写入 `nce.classroom.backup.<clientSessionId>`，服务端确认成功才清除，保留最新 10 条。提交失败时可以拿备份原样重新 POST。
- **作业布置文本**：可以在课堂「作业检查」侧栏边上课边写，随提交落库；也可以课后在 session 详情页填写。

提交成功后落地到 session 详情页。

## 补录过去的课

课前配置页带 `?backfill=1` 进入补录。补录与正常上课走同一套本地课堂和同一个提交接口，提交内容的结构完全一样，区别只在上课时间由老师指定、课堂页不走倒计时。

## 编辑上课记录

已结束的课可以重新打开编辑，复用的仍是课堂页：

- 服务端在 session 详情里返回一份 `ledger`——这节课的原始快照（分组、成员、逐条计分事件、背书作业检查、奖章），前端据此反向还原成一节本地课堂，并打上「正在编辑哪节课」的标记。
- 因为复用同一个本地槽位，该班有进行中课堂时不能编辑，会被冲突页拦下。
- 结束时走覆盖提交，原地重写同一节课：session 的 id 和幂等键不变，子记录全部重写。

覆盖提交与首次提交有三点不同：

| | 首次提交 | 覆盖提交 |
|---|---|---|
| 默认分组 | 回写 | 不回写——改旧课不该打乱班级现在的分组 |
| 作业布置 | 随提交落库 | 不动，作业只在 session 详情页改 |
| 考勤更正（请假、补课） | 无 | 保留已有更正及其分组座位 |

## 提交契约必须向后兼容

课堂进行中服务端可能发布新版本，而老师浏览器里跑的还是旧页面——这节课结束时，旧页面发出的提交必须照常入库，否则整节课的数据就丢了。所以提交契约按 protobuf 的方式演进：

1. 服务端永不新增必填字段，新字段一律可选并带默认值。
2. 不收紧校验，不改字段名，不改字段语义。
3. 未知字段静默忽略，这样新页面对旧服务端也安全。

浏览器里存的本地课堂结构同理，只能加可选字段：发版后老师刷新页面，新代码要能读出旧结构存下的进行中课堂。

这组约束有专门的测试守卫。测试挂了说明契约被破坏，应该改实现，而不是改测试。

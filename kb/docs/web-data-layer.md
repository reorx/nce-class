# React SPA 开发指南：HTTP 请求、Query 缓存与数据一致性

写给设计、开发和重构 React Single Page Application 的开发者：如何组织 HTTP 请求与业务 hooks，如何让页面往返及时显示内容，以及如何在缓存、写操作、身份和本地草稿之间保持一致。本指南基于 NCE Class 两次重构的计划、实施 session、提交和当前代码，是本项目 Web 数据层的开发规范，也供同类 SPA 复用。

“必须”表示数据正确性与职责边界；缓存秒数、文件数量和特定业务处理是本项目的选择，移植时需要重新评估。实际代码与历史计划不一致时，以已核对的实现和测试为事实依据；已发现但未解决的差距单独列出，不把计划中的承诺当成已实现能力。

## 1. 从用户体验定义目标

初始问题是收银台列表 → 收款项详情 → 返回列表时反复等待、内容短暂空白。原项目已有集中式 fetch 封装，问题主要来自响应只放在组件 state、卸载后丢失，以及写后刷新依赖各调用方传 reload 回调。

本类改造的目标有四个：已访问页面能复用数据；过期刷新不清空已有内容；一次写入让所有相关页面最终一致；缓存变化不损坏用户正在编辑的内容。验收不能只检查“已使用 useQuery”，也不能以所有场景零网络请求为目标。

用户确认的原始方向保留：HTTP API → 领域 Query/Mutation → React 组件；只迁移 Web；继续使用 fetch。新项目可选择 Axios，但 HTTP 库的选择与缓存方案独立。给已有 fetch 项目加缓存，无需同时更换 HTTP 库。小程序的 Taro 请求、Bearer 身份及生命周期留在其自身边界内。

## 2. 按职责和领域组织代码

```text
组件 / 页面
    ↓ 领域 hooks
queries/<domain>  ──→ keys、cache-effects、会话与 Mutation 公共机制
    ↓ 纯请求函数
api/<domain>     ──→ HTTP client
    ↓
服务端 API
```

| 层 | 负责 | 不承担 |
|---|---|---|
| HTTP client | cookie/header、JSON、204、状态码、网络错误、取消信号 | 导航、Toast、业务缓存、叠加重试 |
| 领域 API | 请求函数、输入/响应类型、原样传递协议 | React 状态、QueryClient、页面交互 |
| 领域 Query/Mutation | key、读取条件、时效、预取、写后缓存、并发及身份边界 | 表单 draft、弹窗开关、业务展示 |
| React 组件 | 渲染、交互、编辑草稿、成功后的关窗与导航 | 拼 URL/key、另存服务器响应再手动 reload |

API 与 Query 都按 classes、students、sessions、billing 等业务领域分文件。DTO 与 API 放在所属领域；跨领域使用类型导入。纯派生逻辑放 lib，与网络及 React hooks 分开。

命名保持显式：`getBillingBatch`、`listBillingBatches`、`confirmInvoice`；`billingBatchQueryOptions`；`useBillingBatchQuery`、`useConfirmInvoiceMutation`；`billingKeys.detail(id)`、`billingKeys.lists()`。参数化列表另用 `list(params)`，保留可整体失效的 lists 前缀。

每个读取提供一份 queryOptions，普通 hook、预取和确有需要的命令式读取复用它。组件预取通过领域辅助 hook，不另写请求或 key。上节课这类组合读取复用底层缓存，不建立第二份相同响应。

写操作的 variables 使用单对象；后端字段放在 input/payload 等明确位置，classId、batchId 等缓存关联上下文可以作为同级字段，但不能混入请求体。hooks 返回标准 Query/Mutation 结果，不重新发明一套请求状态协议。本项目读取 hooks 仅开放 enabled；有具体需求时再增加 select 等选项，不暴露任意覆盖 queryKey/queryFn/核心生命周期的入口。

公共封装应解决真实共性：本次增加了会话代次和 Mutation 公共机制，目的是统一旧会话响应保护、写后处理与敏感状态清理。不要从领域 hooks 退化成 `useApiQuery(url)`，也不为每一层再增加无行为的转发层。

## 3. HTTP 契约先稳定，再调整调用方

搬迁 API 时保持 method、URL、body、响应及错误语义不变；先写契约测试再搬代码。字段未传、传 null、传空串可能有不同含义；不能因重构统一成一种。例如学生中文名未传表示保持，空串表示清除；重算接口不带 body 与带条款 body 也不同。

错误至少区分 HTTP 错误、传输失败、取消。HTTP 错误保留 status，网络错误保留 cause 并提供稳定文案，取消不转换成普通失败。错误响应不是合法 JSON 时有兜底信息。类型断言只表达编译期契约，不等于运行时响应校验。

读取的取消信号必须贯穿 queryFn → 领域 API → fetch。HTTP 层不重复重试、不自动跳登录、不弹 Toast；低层传播错误，查询/交互边界决定怎么处理。取消读取能阻止旧结果回填，但不能据此声称已撤销服务端正在执行的写操作。

## 4. Key、时效和读取依赖

key 表达“这份服务器数据是什么”，不是“哪个组件正在看”。同一资源由多个页面消费时共享 key；会影响服务端响应的 ID、分页、排序、筛选、租户范围必须参与身份判定。纯客户端筛选不拆成多个相同请求的缓存。本项目按登录会话整体隔离；可在同一登录下切换机构的项目还需要机构维度或等效隔离流程。

浏览器 SPA 的 QueryClient 放在稳定根部，不随路由创建；测试每例独立创建。这个约定不适用于跨请求共享用户数据的 SSR 服务端实例。

| 本项目配置 | 取值及目的 |
|---|---|
| 普通业务与 me 的 staleTime | 30 秒，短时往返复用 |
| 老师列表、奖章库 staleTime | 5 分钟，减少低频数据请求 |
| 无订阅缓存 gcTime | 30 分钟，跨页返回仍可显示旧内容 |
| 读取 retry | 仅网络错误、5xx 至多一次；4xx 不重试 |
| 写入 retry | false；与离线暂停/恢复是两件事，见后文 |
| 持久化与同步 | 内存缓存；不持久化，不跨标签广播，不承诺实时同步 |

staleTime 表示多久视为新鲜，不是轮询间隔；gcTime 决定无人订阅后的回收时间。普通查询在过期后挂载、聚焦或重连时允许刷新。长缓存不能替代写后失效；失效也不能发现所有其他客户端的更新。[官方默认行为](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)

独立读取并行启动；真正依赖返回 ID 的查询用 enabled。缺 ID、弹窗未打开时不发请求；不能靠空字符串路径试错。不要将原来可并行的老师、身份、奖章读取串成瀑布。

列表 hover/focus 可预取用户即将打开的完整详情，复用同一 options。不要预取全部机构数据，不要把不含明细的列表摘要写成完整详情。预取未完成、失败或缓存已回收时仍需要正常加载反馈。

## 5. 页面状态由“有没有数据”优先决定

| 状态 | 展示规范 |
|---|---|
| 无数据，首次请求中 | 保留页面框架，显示区域加载 |
| 无数据，首次失败 | 错误与适当重试；403/404 给对应语义 |
| 成功返回空集合 | 业务空态，与加载/失败区分 |
| 有数据，后台刷新 | 持续显示内容，仅轻量提示刷新 |
| 有数据，后台失败 | 显示旧内容并标明刷新失败，允许重试 |
| 缺必要条件，查询未启用 | 等待选择等 idle 提示，不永久转圈 |
| 网络暂停 | 表达等待联网；不能仅由 pending 推断请求已发出 |

有 data 时，不能用 isFetching 把整页换成加载页。切换不同实体时只使用目标 key 的数据，不能让上一位学生或上一个批次短暂冒充新目标。

本项目把口径抽到 queryView，展示统一用 QueryState。后台错误从 QueryCache 通知，每次失败不随观察者数量重复；再以相同文案 4 秒去重抑制断网时的提示洪峰。这个时间是产品选择，非 Query 库要求。首次错误由页面处理，取消不提示，401 进入身份流程。

当前 queryView 将无数据的 paused 状态归入 loading，尚无独立等待联网展示；不可把上表的完整目标描述成每个分支都已落地。

## 6. 写后缓存维护是业务规则的一部分

每个 Mutation 必须回答：响应能回写什么？哪些派生数据失效？哪些实体已删除？归属 ID 从哪里来？其规则集中在按业务动作命名的 cache-effects，由领域 hook 调用，不由页面散落的 reload/onSaved 维护。

| 响应/动作 | 处理方式 |
|---|---|
| 完整、同形状详情 | 取消该 key 的在途旧读取，再回写完整响应 |
| 单行/局部响应 | 仅更新确定的对应字段；其他详情或汇总失效重读 |
| 提交结果/列表摘要 | 不强转成完整详情；由详情查询获取所需数据 |
| 删除实体 | 移除实体缓存，停用仍挂载的详情查询；处理列表和关联实体 |
| 服务端业务快照 | 刷新展示不等于重新执行业务计算 |

只处理当前详情不够：改学生姓名还影响成长档案、历史课堂、考勤、收费；确认收款影响批次和列表合计；改排班影响周期与收费展示。优先通过上下文 ID 精确定位，缺失时从缓存推断；仍无法判定则对相关领域保守失效，不为定位归属额外发请求，也不一律全站刷新。

失效通常只立即重取活跃查询，非活跃查询保留旧数据、下次使用再刷新。因此“已失效”不等于“返回首帧必然已更新”。删除批次是确定结果，可以先从已有列表移除该项再失效；收款合计包含服务端规则，应重读，不能用前端猜算换取视觉上的立即一致。验收需区分确定的同步更新和标明刷新中的最终一致。

写后维护放在 hook 的 onSuccess，组件提前卸载也要执行。维护 Promise 可保持按钮 pending 到相关活跃查询刷新完成。本项目不把读刷新失败升级成写失败；否则用户会重复提交已经成功的写操作。不要让可预期的读取错误从 onSuccess 抛出；程序错误也不能通过全面吞异常掩盖。

回写新响应前处理在途旧 GET，是防止数据倒退的必要步骤。删除还需关注 observer：单纯 remove 缓存后，仍启用的详情 hook 可能重新建立查询，向刚删除的对象发 404 请求。当前批次详情从删除进行中就停用读取。

## 7. 即时交互、草稿与服务器缓存分别管理

Query 负责服务器快照，表单 draft 负责用户尚未确认的编辑，Mutation pending 表达未完成操作。不要把三者塞入同一个 state。

普通表单在开始编辑时建立 draft，背景读取只更新服务器快照，不覆盖输入。保存中如果用户又作修改，旧保存成功回调不能清掉新编辑。资源、作业、收费条款、分组拖拽都遵守这个边界。能从响应计算的筛选、统计直接派生，不用 effect 再复制进 state。

即时反馈不一定需要乐观改缓存。考勤采用确认记录 + pending overlay：进行中修改只叠加显示，失败时撤去对应格，整表后台刷新不会覆盖 pending 格。锁按 sessionId + studentId，而非锁整页；其他格可并行。撤销栈只收录成功修改，撤销失败仍可重试。成功时回写该格，必要时重启早于写入的表格请求，防止旧快照盖回已确认值。

收费确认采用成功后更新，不提前显示已到账。是否采用乐观缓存或 overlay，应取决于失败回滚、并发粒度和业务后果，不必全项目一种模式。

## 8. “展示缓存”与“建立业务底稿”需要不同新鲜度

已有数据适合立即展示，但未必适合固化成新的业务记录。课前名单、历史课堂编辑底稿要在本次进入后读取成功，才建立本地 draft；即使缓存仍在 30 秒内也重读。排班编辑只要求详情未过期。本项目通过专门的 latest hooks 表达差异，普通页面继续复用缓存。

强制读取不等于后台每次成功都重建 draft：本次初始化完成后，后续读取不得重置它。当前 latest hooks 使用挂载时强制刷新；调用方综合“本次挂载后已读取、当前不在读取、没有失败”判断可定稿。仅从 disabled 切为 enabled 不能当成强制刷新新鲜缓存的保证；测试必须覆盖实际启用顺序。

这是对“切换页面都不请求”的限制：业务正确性要求最新输入时，接受明确的一次等待。当前课前配置每次都等名单，离线无法新开课；恢复已有本地课堂则是另一种契约。

## 9. 身份是缓存边界，也是页面生命周期边界

身份至少区分：未确定、已登录、确认未登录、读取失败。本项目 me 对象表示已登录，null 表示确认未登录，undefined + error 表示暂时读不到。网络失败、5xx、403 不等于退出；登录请求的 401 是凭据错误，不能按既有会话过期处理。

切换身份时递增会话代次、取消在途查询、移除旧服务端缓存、更新 me；旧会话写响应和旧 401 不得污染或注销新会话。仅清缓存不足以约束稍后完成的异步回调，领域 Mutation 还需检查代次。本项目保留 me 的 Query 对象原地更新，确保挂载的身份观察者收到通知，而非仅调用 clear。

认证状态只保有一个来源；me props 可以传递这份数据，不必每个展示组件都独立调用 hook。密码类 Mutation 完成后 reset，并缩短结果保留时间；不持久化敏感 variables。

导航只由一处决定。主动退出不保留前一个账号的来处；被动过期可在重新登录后恢复来处。实际浏览器发现守卫 Navigate 与退出回调 navigate 的先后顺序不同于 jsdom，因此最终由守卫统一跳转。规则应消除竞争，而非依赖两次导航“通常谁最后执行”。

身份就绪前后保持同一组件树；不能通过换一层 Guard 意外重挂载工作页并丢失其 UI 状态。

## 10. 本地优先业务必须贯穿整个入口与提交链

课堂规则详见[课堂生命周期](classroom-session-lifecycle.md)。可复用经验是：如果业务承诺离线继续工作，除了保存 localStorage，还要验证应用启动、身份守卫、数据初始化和联网后的跳转。

本机有进行中的课堂时，身份读取中或失败也可恢复；只有确认未登录才进入登录流程。这个例外只允许继续本地工作，不能绕过服务端授权。Query 缓存可清除，本地课堂与备份不可随账号切换顺手删除；其他项目应明确本地草稿的账号归属，不能直接照搬本项目按班级存储的规则。

建课堂前重新检查本地状态，定稿只执行一次，防止 StrictMode、晚到查询或后台刷新重复生成幂等键、覆盖已有课堂。本项目把进入判定抽成纯函数，降低组件 effect 交错的复杂度。

提交前冻结 payload 并持久化备份。同一份未变课堂重试，包括刷新页面后的重试，复用 payload、结束时间和幂等键；内容变化才重新冻结。只有服务端确认成功才清备份，后续刷新失败不能再报提交失败。服务端幂等契约仍是可靠性的基础；本项目同键已成功提交后的后续修订应走历史课堂编辑，不能将“换 payload 保留同键”推广成通用幂等协议。

断网恢复后，写成功而 me 仍处于“无数据且读取失败”时，本项目会在写 resolve 前重读 me，避免跳详情后卡在身份错误页。这是本地优先入口带来的衔接需求，普通已知身份写操作不额外读 me。

## 11. 必须单独定义离线写入语义

本次复盘确认一处未实现的计划承诺：`retry: false` 关闭失败后的重试，不等于禁止暂停写入联网后继续。当前 QueryClient 没有显式配置 networkMode，使用默认 online；本地安装版本的最小复现中，离线 mutate 的函数未执行、状态为 paused，恢复在线后无需再次点击就执行了一次。这与原 Plan 的“不做离线排队和自动重放”表述不同。[官方 Network Mode](https://tanstack.com/query/latest/docs/framework/react/guides/network-mode)

规范要求分别决定：离线发起时拒绝、尝试后快速失败，还是明确暂停等待联网；暂停期间如何显示、取消，以及切账号后是否仍能执行。不能仅凭 retry:false 声称已实现这些保障。

如业务选择禁止延后执行，应在后续修复中明确网络模式、提交前检查及恢复测试；若选择支持暂停，必须有可见状态、会话绑定和恢复时校验。会话代次只限制本地缓存回填，不能阻止已发出的服务器写入，也不自动阻止暂停中的请求使用变化后的 cookie。

本次只记录该差距，未修改运行代码；见 [known-issues](../known-issues.md)。未据此宣称已经发生线上错账或跨账号写入。

## 12. 重构工作流与验收

先清点接口与调用方，再迁基础层，最后迁组件。每个清单条目包含：业务场景、API 契约、读取条件、key、缓存时效、写后影响、草稿来源、验收行为。只搜索 fetch 会漏掉已封装的调用和类型引用；文本扫描还需排除注释误命中。

基础层阶段保持旧签名的兼容桥，旧写操作也调用同一缓存规则；新 hooks 直接调用新 API，防止双重维护。组件迁移按业务链路分批，基础层可先提交但不能提前宣布用户症状已解决。所有调用方及类型迁移后删除兼容桥，防止形成永久双轨。

测试分层：

| 层级 | 验证内容 |
|---|---|
| API 契约 | 每个方法的 URL/method/body，缺省值，204，错误，signal |
| Query/Mutation | 去重、fresh/stale/gc、依赖、取消、旧响应、会话切换、完整失效矩阵 |
| 页面集成 | 真 App + Router + Provider + 假 fetch，验证跨页导航、写后显示、draft、守卫和并发 |
| 浏览器 | 路由竞争、页面重挂载、真实渲染、离线/恢复、生产构建网络证据 |

先写行为用例再修改对应逻辑。缓存矩阵同时放两个班级的数据，既验证目标更新，也验证无关数据没有被误改。延迟响应验证“旧 GET 晚于写返回”和“新账号登录后旧请求才结束”。不要只断言 invalidateQueries 被调用，不要通过 mock 所有 hooks 跳过真正的缓存行为。

测试 harness 要读取组件实际依赖的 tracked 字段，观察者异步通知用 waitFor 等待条件；一次 mutateAsync resolve 不代表 DOM 已同步完成。用受控 Promise 模拟时序，避免固定 sleep 掩盖竞争。模拟在线状态与让 fetch 报网络错是不同测试，二者都需要。

浏览器性能验收区分冷启动、fresh 返回、stale 返回、回收后重进；同时观察首帧 DOM 和请求数。开发 StrictMode 的中止/重挂载不能作为生产重复请求的直接证据，最终使用生产构建录 HAR。浏览器未能注入延迟时，可由页面测试证明延迟状态，报告应写清证据来源。

测试写入使用数据库副本；SQLite WAL 数据库采用 `.backup`，不能直接 cp 主文件。截图、HAR 归档到 tmp 的日期任务目录，清理本次浏览器会话。只有线上核对完成才关闭部署后检查，不因本地测试通过自动删 next-up。

## 13. 执行过程与原计划的差异

以下是本项目经验的来源，而非其他项目必须照搬的提交拆分：

| 阶段与证据 | 实际工作与修正 |

原设计经过实践细化的主要地方：

- 三层结构保留，新增公共机制只承担会话/Mutation 的真实共性；variables 和 key factories 进一步统一。
- 考勤从可选乐观回滚方案落实为 pending overlay；整表读取与局部写并发也有保护。
- “清空所有缓存”改成保留身份 Query 对象、原地通知；业务缓存清理与本地草稿分离。
- “写后失效”补上取消在途 GET、删除时立即修正列表、停用被删除详情查询。
- 缓存优先展示保留，但建立课堂底稿时明确选择最新读取；不能将省请求置于正确名单之前。
- 本地优先扩展到身份守卫、稳定组件树和联网后身份恢复；提交冻结跨刷新保持，课堂内容变化时重新冻结。
- 自动测试没有发现所有浏览器导航竞争；最终验收补上生产构建与 HAR。
- 本次复盘发现离线写入暂停语义尚未符合原计划，已独立记录，不能包装为完成的优化。

历史 session 报告 Plan 1 Web 468 个、Plan 2 Web 513 个测试通过，均通过 tsc/build 与当时的 server 292 个测试；这些是对应提交的历史结果，本次复盘未重新跑全量测试。现存生产预览网络摘要显示首次 me、列表、预取详情各一次，约 35 秒后才再次读取详情与列表；结合 session 的 DOM 观察，支持本地往返缓存目标已验收，不证明生产环境已经核对。

当前 next-up 仍留有 Web 迁移部署后的收银台、换账号和离线课堂核对；本次未操作生产。离线课堂后台 Toast 的打扰、强制最新名单带来的等待、大 chunk 提示是 session 记录的取舍或后续观察点，不列成已解决性能问题。

## 14. 新增或评审功能的最小清单

1. 请求契约、错误分类、取消信号是否明确，是否已有可复用 API？
2. key 是否包含影响响应的参数，是否与已有查询共享，身份范围是否隔离？
3. 查询何时启用，哪些并行，哪些依赖，是否需要最新底稿？
4. 首次/空态/错误/后台刷新/暂停是否区分，已有数据会不会被清空？
5. Mutation 回写、失效、删除各处理哪些数据，在途旧请求会不会覆盖结果？
6. 保存成功与刷新失败是否分开，局部并发与重复点击是否有规则？
7. 表单、本地业务状态、pending 是否分开，后台刷新或树变化会不会丢编辑？
8. 登录、退出、旧响应、离线恢复和服务端幂等边界是否有测试？
9. 是否先写行为测试，并以实际浏览器与网络证据验证用户最初反馈？
